# Learning Content Week 02: ฮาร์ดแวร์ ซอฟต์แวร์ และระบบนิเวศสมัยใหม่

> ใช้คู่กับ [[Week 02 - Hardware & Software Ecosystems]] สำหรับอ่านก่อนเรียน ทบทวนหลังเรียน และเตรียมกิจกรรมปฏิบัติการ

## คำถามนำ
โปรแกรมหนึ่งตัวทำงานผ่านชั้นฮาร์ดแวร์ ซอฟต์แวร์ และระบบปฏิบัติการอย่างไร?

## ผลลัพธ์การเรียนรู้ย่อย
1. อธิบายลำดับชั้น hardware-firmware-OS-application
2. เข้าใจ CPU/GPU/NPU, หน่วยความจำ, storage และ I/O
3. เชื่อม edge computing กับ green computing

## แก่นความรู้ที่ต้องเข้าใจ
- คอมพิวเตอร์ทำงานเป็นชั้น: hardware ให้ทรัพยากร, OS จัดการทรัพยากร, application แก้ปัญหาผู้ใช้
- memory hierarchy คือการแลกเปลี่ยนระหว่างความเร็ว ราคา และขนาด ตั้งแต่ register/cache/RAM/storage
- edge computing ย้ายการประมวลผลเข้าใกล้แหล่งข้อมูล ส่วน green computing ทำให้การออกแบบระบบต้องคิดเรื่องพลังงานตั้งแต่ต้น

## เนื้อหาเรียนรู้
- ให้เริ่มจากคำสั่งง่าย ๆ เช่นเปิดไฟล์หรือกดปุ่มในเกม แล้วตามรอยว่าคำสั่งเดินทางผ่าน application, system call, OS, driver, storage และ CPU อย่างไร
- เปรียบเทียบ CPU, GPU และ NPU ด้วยชนิดงาน: CPU เหมาะงานทั่วไปและควบคุมลำดับ, GPU เหมาะงานขนาน, NPU เหมาะ inference ของ AI บนอุปกรณ์
- โยงไปยังการออกแบบที่รับผิดชอบ: ถ้าระบบ AI ประมวลผลบน edge ได้ จะลด latency และลดการส่งข้อมูลบางส่วนขึ้น cloud แต่ต้องคุมพลังงาน ความร้อน และการอัปเดตซอฟต์แวร์ให้ดี

## 🧭 อธิบายเพิ่มเติม (ฉบับขยาย)

### 1. ชั้นของระบบเหมือน "ร้านอาหาร"
ลองนึกถึงร้านอาหารหนึ่งร้าน ลูกค้า (ผู้ใช้) สั่งอาหารผ่านพนักงานหน้าร้าน (application) พนักงานส่งใบสั่งเข้าครัวตามแบบฟอร์มของร้าน (library/runtime) หัวหน้าครัว (OS kernel) จัดคิวว่าใครทำเมนูไหนก่อน ใช้เตาไหน และเก็บวัตถุดิบไว้ที่ใด พ่อครัวแต่ละคนที่รู้วิธีใช้เครื่องมือเฉพาะ (device driver) เป็นคนสั่งเครื่อง ส่วนคู่มือในตัวเตาอบ (firmware) ควบคุมอุณหภูมิจริง และเตา ตู้เย็น มีด (hardware) คือทรัพยากรทางกายภาพ

จุดสำคัญคือ **ไม่มีลูกค้าคนใดเดินเข้าครัวไปเปิดเตาเอง** เช่นเดียวกับโปรแกรมทั่วไปที่ไม่ได้สั่งฮาร์ดแวร์โดยตรง แต่ต้องขอผ่าน OS ด้วย **system call** ทำให้ระบบปลอดภัยและแบ่งทรัพยากรได้อย่างเป็นธรรม

![แผนภาพชั้นของระบบ 7 ชั้น จากผู้ใช้ application library OS kernel device driver firmware จนถึง hardware พร้อมลูกศรแสดงคำสั่ง Save ในเกมเดินทางลง 6 ขั้นจนเขียนลง flash ของ SSD แล้วผลลัพธ์ย้อนกลับขึ้นมา](/images/weeks/w02-layers.svg)

### 2. ตามรอยทีละขั้น: กด "Save" ในเกม Mini-Project
งาน Lab 02 ให้ทำระบบ Save/Load ดังนั้นลองดูว่าเมื่อเรียก `save_game()` เกิดอะไรขึ้น
1. **Application:** โค้ดเกมแปลงสถานะผู้เล่นเป็นข้อความ JSON แล้วเรียก `open("save.json", "w")` และ `write()`
2. **Runtime:** Python เก็บข้อความไว้ใน buffer ในหน่วยความจำก่อน เพื่อไม่ต้องเรียก OS ทุกตัวอักษร
3. **System call:** เมื่อ buffer เต็มหรือปิดไฟล์ Python เรียก system call ของ OS (บน Linux คือ `write`, บน Windows ผ่าน `WriteFile`) CPU สลับจาก user mode เข้า kernel mode
4. **OS kernel:** ระบบไฟล์หาว่าไฟล์อยู่บล็อกไหนของดิสก์ อาจพักข้อมูลไว้ใน page cache บน RAM ก่อน
5. **Driver + Firmware:** ไดรเวอร์ส่งคำสั่ง NVMe ไปยัง SSD จากนั้น firmware ในตัว SSD เลือกตำแหน่งเซลล์ flash ที่จะเขียน
6. **Hardware:** ข้อมูลถูกเขียนลงชิป flash และอยู่ต่อได้แม้ปิดเครื่อง (non-volatile)

ผลลัพธ์ย้อนกลับขึ้นมาเป็นค่าที่บอกว่าเขียนสำเร็จหรือไม่ บทเรียนเชิงปฏิบัติคือ ถ้าเกมปิดตัวกะทันหันก่อนข้อมูลออกจาก buffer ไฟล์ save อาจไม่ครบ จึงควรใช้ `with open(...)` เพื่อให้ไฟล์ถูกปิดเสมอ รายละเอียดหน้าที่ของ OS และ system call อ่านต่อที่ [[Week 02/02_ระบบปฏิบัติการสมัยใหม่และคอนเทนเนอร์]]

### 3. Memory hierarchy: ทำไมต้องมีหน่วยความจำหลายชั้น
เปรียบเหมือนการทำการบ้าน: ของที่ใช้ตอนนี้วางบนโต๊ะ (register/cache) หนังสือที่ใช้บ่อยอยู่บนชั้นข้างโต๊ะ (RAM) และหนังสือทั้งหมดอยู่ในห้องสมุดของคณะ (SSD/HDD) โต๊ะเล็กแต่หยิบได้ทันที ห้องสมุดใหญ่แต่ต้องเดินไปไกล ถ้าทุกอย่างอยู่บนโต๊ะได้ก็ดี แต่โต๊ะใหญ่ขนาดนั้นแพงมากและเปลืองพลังงาน

![กราฟแท่งแบบ log scale แสดง latency โดยประมาณของ register 0.3 ns, L1 1 ns, L2 4 ns, L3 15 ns, RAM 100 ns, SSD 100,000 ns และ HDD 10,000,000 ns พร้อมเทียบว่าถ้า 1 ns เท่ากับ 1 วินาที การอ่าน SSD จะนานราว 1 วัน และ HDD ราว 4 เดือน](/images/weeks/w02-memory-latency.svg)

ตัวเลขในภาพเป็นลำดับขนาดโดยประมาณ ค่าจริงขึ้นกับรุ่นของเครื่อง แต่สิ่งที่ต้องจำคือ **ระยะห่างแบบทวีคูณ** RAM ช้ากว่า L1 ราว 100 เท่า และ SSD ช้ากว่า RAM ราว 1,000 เท่า ระบบจึงพึ่ง **locality** คือข้อมูลที่เพิ่งใช้มักถูกใช้อีก (temporal) และข้อมูลที่อยู่ติดกันมักถูกใช้ต่อกัน (spatial) cache จึงเก็บข้อมูลเป็นก้อน (cache line) แทนทีละไบต์ ดูกลไก cache, MMU และ virtual memory ใน [[Week 02/01_สถาปัตยกรรมระดับฮาร์ดแวร์เชิงลึก]] และทดลองวัดเวลาอ่านจาก RAM เทียบไฟล์ได้ใน Lab 02 ขั้นตอนที่ 5

### 4. CPU, GPU, NPU: เลือกเครื่องมือให้ตรงงาน
- **CPU** เหมือนเชฟมือหนึ่งไม่กี่คน ทำเมนูซับซ้อนได้ทุกแบบ ตัดสินใจเปลี่ยนขั้นตอนได้เร็ว เหมาะกับงานที่มีเงื่อนไขมาก
- **GPU** เหมือนพนักงานหั่นผักหลายพันคน แต่ละคนทำงานง่าย ๆ เหมือนกันพร้อมกัน เหมาะกับงานกราฟิกและการ train โมเดล
- **NPU** เหมือนเครื่องจักรในสายพานที่ออกแบบมาทำงานเดียว คือคูณ-บวกเมทริกซ์ของ AI จึงเร็วและประหยัดไฟมากสำหรับ inference บนอุปกรณ์

![เปรียบเทียบโครงสร้าง CPU ที่มีคอร์ใหญ่ไม่กี่คอร์และ cache ใหญ่ GPU ที่มีคอร์เล็กจำนวนมาก และ NPU ที่เป็นอาร์เรย์ตัวคูณ-บวกให้ข้อมูลไหลผ่านเป็นจังหวะ พร้อมงานที่เหมาะกับแต่ละแบบ](/images/weeks/w02-cpu-gpu-npu.svg)

ชิปสมัยใหม่อย่าง SoC ในมือถือและโน้ตบุ๊กรวมทั้งสามแบบไว้ด้วยกัน (heterogeneous computing) งานของนักพัฒนาคือส่งงานแต่ละส่วนไปยังหน่วยที่เหมาะ อ่านต่อที่ [หัวข้อ 5](/module/02/05)

### 5. ตารางเปรียบเทียบ Cloud กับ Edge

| ประเด็น | Cloud computing | Edge computing |
|---|---|---|
| ประมวลผลที่ไหน | data center ระยะไกล | ใกล้แหล่งข้อมูล เช่น กล้อง เกตเวย์ มือถือ |
| Latency | สูงกว่า เพราะต้องส่งข้อมูลไป-กลับผ่านเครือข่าย | ต่ำ ตอบสนองได้ทันที |
| พลังประมวลผล | สูงมาก ขยายได้ตามต้องการ | จำกัดด้วยขนาด พลังงาน และความร้อน |
| ความเป็นส่วนตัว | ข้อมูลดิบต้องออกจากอุปกรณ์ | ส่งเฉพาะผลสรุปได้ ข้อมูลดิบอยู่ในเครื่อง |
| ความท้าทาย | ค่าใช้จ่ายเครือข่าย การพึ่งอินเทอร์เน็ต | อัปเดตซอฟต์แวร์จำนวนมาก ความปลอดภัยของอุปกรณ์ |
| ตัวอย่าง | train โมเดลภาษาใหญ่ | กล้องตรวจจับคนบุกรุกที่แจ้งเตือนเองได้ |

ในงานจริงมักใช้ร่วมกัน: edge ทำงานเร่งด่วน cloud ทำงานหนักและเก็บข้อมูลระยะยาว ดู [[Week 02/03_สถาปัตยกรรม_Edge_Computing]] ส่วนเรื่องพลังงานและค่า PUE ของ data center ดู [[Week 02/04_Green_Computing]]

### 6. อ่านสเปกเครื่องให้เป็น
เวลาเลือกเครื่องสำหรับเรียนเขียนโปรแกรมและ AI ให้ดูทั้งระบบ ไม่ใช่แค่ความเร็ว CPU
- **RAM:** ถ้าไม่พอ OS จะย้ายข้อมูลไป swap บน SSD ซึ่งช้ากว่าหลายพันเท่า เครื่องจึงช้าลงชัดเจน
- **Storage:** SSD ทำให้เปิดโปรแกรมและโหลดโปรเจกต์เร็วกว่า HDD มาก
- **GPU/NPU:** สำคัญเมื่อ train หรือรันโมเดล AI ในเครื่อง
- **Logical vs physical core:** `os.cpu_count()` นับ logical CPU ซึ่งอาจเป็นสองเท่าของคอร์จริงเมื่อมี SMT/Hyper-Threading

### สรุปสั้น
- ระบบเป็นชั้น: application → runtime → OS → driver → firmware → hardware โปรแกรมขอใช้ฮาร์ดแวร์ผ่าน system call
- OS จัดการ process, memory, file และ device เป็นตัวกลางที่ทำให้ปลอดภัยและแบ่งทรัพยากรได้
- memory hierarchy แลกความเร็วกับขนาดและราคา ระยะห่างของ latency เป็นแบบทวีคูณ และอาศัย locality
- CPU เหมาะงานทั่วไป GPU เหมาะงานขนาน NPU เหมาะ AI inference ที่ประหยัดไฟ
- edge ลด latency และเก็บข้อมูลดิบไว้ใกล้แหล่ง cloud ให้พลังประมวลผลสูง ระบบจริงใช้ร่วมกัน

## Research เพิ่มเติมและแหล่งอ้างอิง
**หัวข้อวิจัยเสริม:** Hardware/software ecosystem, edge และพลังงาน

- ระบบสมัยใหม่มี heterogeneous computing: CPU ทำงานทั่วไป, GPU/NPU เร่งงานขนานและ AI inference ทำให้ผู้เรียนต้องอ่านสเปกเครื่องมากกว่าแค่ความเร็ว CPU
- Edge computing ลด latency และลดการส่งข้อมูลขึ้น cloud แต่เพิ่มโจทย์ด้าน update, security, observability และพลังงานของอุปกรณ์ปลายทาง
- Green computing ควรเชื่อมกับการเลือก hardware, power profile, sleep mode และการออกแบบ workload ไม่ใช่พูดเฉพาะการประหยัดไฟทั่วไป
