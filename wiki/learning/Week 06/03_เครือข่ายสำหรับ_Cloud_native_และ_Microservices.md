# เครือข่ายสำหรับ Cloud native และ Microservices

ในทศวรรษที่ผ่านมา การออกแบบซอฟต์แวร์ได้เปลี่ยนกระบวนทัศน์จากระบบก้อนเดียว (Monolithic) ไปสู่สถาปัตยกรรมแบบ **Microservices** และการทำงานบนสภาพแวดล้อม **Cloud-native** ความเปลี่ยนแปลงนี้ไม่ได้กระทบแค่การเขียนโค้ด แต่ได้พลิกโฉม "ระบบเครือข่าย" อย่างสิ้นเชิง ในฐานะวิศวกรคอมพิวเตอร์ เราต้องเข้าใจกลไกเครือข่ายยุคใหม่ที่รองรับการเปลี่ยนแปลงแบบไดนามิกนี้

## ความท้าทายในโลก Cloud-native

ในระบบแบบเก่า เซิร์ฟเวอร์มักมี IP Address ที่คงที่ (Static) การตั้งค่า Firewall หรือ Load Balancer สามารถทำแบบ Manual ได้ แต่ในโลกของ Container (เช่น Docker) และ Orchestrator (เช่น Kubernetes) เซอร์วิสต่างๆ สามารถถูกสร้างใหม่ ย้ายเซิร์ฟเวอร์ หรือถูกทำลายได้ตลอดเวลา (Ephemeral) ทุกๆ วินาที ทำให้การจัดการเครือข่ายแบบเดิมไม่สามารถตอบสนองได้อีกต่อไป

## เทคโนโลยีเครือข่ายหลักสำหรับ Microservices

### 1. Service Discovery
เมื่อ IP เปลี่ยนตลอดเวลา ระบบจำเป็นต้องมีกลไกให้ Microservices ค้นหากันเจออัตโนมัติ Service Discovery ทำหน้าที่เสมือนสมุดหน้าเหลืองแบบไดนามิก เมื่อมี Container เกิดใหม่ มันจะไปลงทะเบียนตัวเอง (Registry) เมื่อบริการอื่นต้องการเรียกใช้ ก็จะไปสอบถาม (Lookup) ผ่านชื่อบริการแทน IP Address โดยตรง

### 2. Software-Defined Networking (SDN) และ Container Network Interface (CNI)
ใน Kubernetes การจัดการเครือข่ายจะใช้ปลั๊กอิน CNI (เช่น Calico, Flannel, หรือ Cilium) เพื่อสร้างเครือข่ายเสมือน (Overlay Network) ครอบทับเครือข่าย Physical เดิม ทำให้ Container ทุกตัวเสมือนว่าอยู่ในวง LAN เดียวกัน สามารถคุยกันได้แม้จะรันอยู่บนโหนด (Node) ต่างกัน

### 3. Service Mesh
เมื่อระบบมี Microservices นับร้อยตัว การเขียนโค้ดจัดการการเชื่อมต่อ การ Retry การยืนยันตัวตน (mTLS) ภายในทุกๆ เซอร์วิสเป็นเรื่องยุ่งยาก **Service Mesh** (เช่น Istio, Linkerd) เข้ามาแก้ปัญหานี้โดยใช้สถาปัตยกรรมแบบ "Sidecar Proxy"
*   ทุกๆ Container จะมี Proxy ขนาดเล็กถูกฝังแนบไปด้วย (Sidecar)
*   เมื่อ Service A จะคุยกับ Service B มันจะส่งข้อมูลไปที่ Proxy ของตนเอง 
*   Proxy จะจัดการเรื่อง Routing, Encryption, และ Metrics ทั้งหมด ก่อนส่งข้ามเครือข่ายไปยัง Proxy ของ Service B
*   สิ่งนี้ทำให้นักพัฒนาสามารถโฟกัสกับ Business Logic ได้อย่างเต็มที่ โดยผลักภาระงานเครือข่ายไปให้ระบบ Infrastructure จัดการ

## ความสำคัญของการทำงานแบบกระจายศูนย์

เครือข่ายใน Cloud-native ต้องออกแบบเพื่อรองรับความล้มเหลว (Design for Failure) ด้วยแนวคิด "Zero Trust Network" ที่สมมติว่าเครือข่ายภายในก็ไม่ปลอดภัย ทุกการสื่อสารต้องถูกตรวจสอบสิทธิ์ และใช้กลไกเช่น Circuit Breaker เพื่อป้องกันไม่ให้ความล้มเหลวของบริการหนึ่งลุกลามไปยังบริการอื่น (Cascading Failure) การเข้าใจสถาปัตยกรรมเหล่านี้คือสิ่งจำเป็นสำหรับการสร้างระบบที่รองรับผู้ใช้งานระดับล้านคนครับ
