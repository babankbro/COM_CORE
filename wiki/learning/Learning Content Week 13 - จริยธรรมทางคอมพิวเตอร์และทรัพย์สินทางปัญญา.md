# Learning Content Week 13: จริยธรรมทางคอมพิวเตอร์และทรัพย์สินทางปัญญา

> ใช้คู่กับ [[Week 13 - Computer Ethics & Intellectual Property]] สำหรับอ่านก่อนเรียน ทบทวนหลังเรียน และเตรียมกิจกรรมปฏิบัติการ

## คำถามนำ
วิศวกรคอมพิวเตอร์ควรตัดสินใจอย่างไรเมื่อเทคโนโลยีกระทบสิทธิ ความเป็นส่วนตัว และสังคม?

## ผลลัพธ์การเรียนรู้ย่อย
1. ใช้กรอบจริยธรรมในการวิเคราะห์กรณีศึกษา
2. เข้าใจ privacy, bias, accountability และ transparency
3. รู้จัก PDPA, copyright, license และ open source

## แก่นความรู้ที่ต้องเข้าใจ
- จริยธรรมคอมพิวเตอร์ไม่ได้ถามแค่ว่าทำได้ไหม แต่ถามว่าควรทำไหม ใครได้ประโยชน์ ใครรับความเสี่ยง และใครรับผิดชอบ
- ACM Code of Ethics ให้กรอบเรื่อง public good, avoiding harm, honesty, privacy และ professional responsibility
- PDPA กำหนดหลักการคุ้มครองข้อมูลส่วนบุคคล รวมถึงบทบาท data controller และ data processor

## เนื้อหาเรียนรู้
- ให้เริ่มจากกรณี AI ตรวจจับใบหน้าในห้องเรียน แล้วถามเรื่อง consent, purpose limitation, data retention, bias และทางเลือกที่ intrusive น้อยกว่า
- อธิบายทรัพย์สินทางปัญญาผ่านงานนักศึกษา: source code, dataset, model weight, prompt, image และ report มีสิทธิและ license ต่างกัน
- โยง open source: การใช้ library ไม่ได้แปลว่าทำอะไรก็ได้ ต้องอ่าน license และให้ attribution ตามเงื่อนไข

## 🧭 อธิบายเพิ่มเติม (ฉบับขยาย)

### 1) จริยธรรม กฎหมาย และนโยบาย ต่างกันอย่างไร
ลองเทียบกับการขับรถ: **กฎหมาย** เหมือนกฎจราจร เป็น "พื้นขั้นต่ำ" ที่ฝ่าฝืนแล้วมีโทษ ส่วน **จริยธรรม** เหมือนมารยาทและความระมัดระวังของคนขับที่ดี ซึ่งไปไกลกว่าที่กฎหมายบังคับ ระบบหนึ่งอาจถูกกฎหมายแต่ยังไม่ควรทำ เช่น เก็บข้อมูลพฤติกรรมผู้ใช้ทั้งที่ไม่จำเป็นต่อบริการ ส่วน **นโยบายองค์กร** (เช่น นโยบายการใช้ AI ในรายวิชา) คือกติกาเฉพาะที่ที่แปลงหลักจริยธรรมให้ปฏิบัติได้จริง

ACM Code of Ethics (ฉบับ 2018) แบ่งเป็น 4 ส่วน: หลักทั่วไป (ข้อ 1.x), ความรับผิดชอบเชิงวิชาชีพ (2.x), ความรับผิดชอบของผู้นำ (3.x) และการปฏิบัติตามประมวล (4.x) ข้อที่ใช้บ่อยในงานนักศึกษาคือ 1.1 สร้างประโยชน์ต่อสังคม, 1.2 หลีกเลี่ยงอันตราย, 1.3 ซื่อสัตย์, 1.4 ยุติธรรมไม่เลือกปฏิบัติ, 1.5 เคารพงานสร้างสรรค์ของผู้อื่น, 1.6 เคารพความเป็นส่วนตัว และ 2.5 ประเมินความเสี่ยงของระบบอย่างรอบด้าน

![แผนภาพ 6 ขั้นตัดสินใจเชิงจริยธรรม เริ่มจากรวบรวมข้อเท็จจริง ระบุประเด็น เทียบ ACM Code ตรวจกฎหมาย PDPA และลิขสิทธิ์ สร้างทางเลือก แล้วบันทึกเหตุผลเพื่อทบทวน](/images/weeks/w13-ethics-decision-flow.svg)

### 2) กรณีศึกษา: ระบบเช็กชื่อด้วยใบหน้าในห้องเรียน
**ข้อเท็จจริง:** คณะต้องการติดกล้องหน้าห้อง ใช้ face recognition เช็กชื่อนักศึกษาอัตโนมัติ ส่งภาพไปประมวลผลบน cloud ของบริษัทผู้ให้บริการ และเก็บภาพไว้ "เผื่อใช้ภายหลัง"

**วิเคราะห์ด้วย ACM Code**
- 1.1/1.2: ได้ประโยชน์คือประหยัดเวลา แต่ความเสี่ยงคือการเฝ้าติดตามตลอดคาบ ข้อมูลรั่วแล้วเปลี่ยนใบหน้าไม่ได้เหมือนเปลี่ยนรหัสผ่าน
- 1.4: model อาจแม่นยำต่างกันตามสีผิว เพศ หรือแสงในห้อง ทำให้บางกลุ่มถูกบันทึกว่า "ขาดเรียน" บ่อยกว่า (algorithmic bias)
- 1.6 และ 2.5: ต้องถามว่าเก็บเท่าที่จำเป็นหรือไม่ และได้ประเมินความเสี่ยงก่อนติดตั้งหรือยัง

**วิเคราะห์ด้วย PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562)**
- ข้อมูลใบหน้าที่ใช้ระบุตัวบุคคลเป็น **ข้อมูลชีวภาพ (biometric)** ซึ่งเป็นข้อมูลอ่อนไหวตามมาตรา 26 โดยหลักต้องได้ **ความยินยอมโดยชัดแจ้ง** และความยินยอมต้องให้โดยอิสระ เมื่อนักศึกษาอยู่ในสถานะที่ปฏิเสธได้ยาก จึงต้องมีทางเลือกอื่นที่ไม่เสียสิทธิ
- บทบาท: มหาวิทยาลัยเป็น **data controller** (กำหนดวัตถุประสงค์และวิธีการ) บริษัท cloud เป็น **data processor** ต้องมีสัญญาประมวลผลข้อมูลกำกับ
- หลัก purpose limitation และ data minimization: ใช้เพื่อเช็กชื่อเท่านั้น เก็บเป็น template แทนภาพดิบ และกำหนดระยะเวลาลบ (เช่น เมื่อจบภาคการศึกษา)
- หากข้อมูลรั่วไหล controller ต้องแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลภายใน 72 ชั่วโมงนับแต่ทราบเหตุ เว้นแต่ไม่มีความเสี่ยงต่อสิทธิของเจ้าของข้อมูล

| ทางเลือก | ประโยชน์ | ความเสี่ยงด้านจริยธรรม/กฎหมาย | ข้อเสนอ |
|---|---|---|---|
| A: ใช้ใบหน้าบังคับทุกคน เก็บภาพไม่มีกำหนด | อัตโนมัติสูงสุด | ข้อมูลอ่อนไหว ไม่มีทางเลือก เก็บเกินจำเป็น | ไม่ควรทำ |
| B: ใบหน้าแบบ opt-in + ทางเลือก QR, ลบเมื่อจบภาค | ยังสะดวก เคารพสิทธิ | ต้องทดสอบ bias และดูแลความปลอดภัย | ทำได้ถ้าครบเงื่อนไข |
| C: QR code ที่เปลี่ยนทุก 30 วินาที | ไม่ใช้ biometric เลย | ต้องป้องกันการส่ง QR ให้เพื่อน | intrusive น้อยสุด |

### 3) ทรัพย์สินทางปัญญาในโครงงานของเรา
เปรียบกับการสร้างบ้าน: เอกสารแบบแปลนที่วาดขึ้นได้ **ลิขสิทธิ์** ทันที, กลไกล็อกประตูแบบใหม่ที่ไม่เคยมีมาก่อนขอ **สิทธิบัตร** ได้, ชื่อและโลโก้ของหมู่บ้านคือ **เครื่องหมายการค้า**, ส่วนสูตรปูนเฉพาะของผู้รับเหมาที่ไม่บอกใครคือ **ความลับทางการค้า** ประเด็นสำคัญคือลิขสิทธิ์คุ้มครอง "การแสดงออก" ไม่คุ้มครอง "ไอเดีย" การเขียนโค้ดใหม่จากแนวคิดเดียวกันจึงไม่ละเมิดลิขสิทธิ์ แต่การ copy โค้ดของคนอื่นมาวางทั้งก้อนละเมิดได้

![ตารางเทียบลิขสิทธิ์ สิทธิบัตร เครื่องหมายการค้า และความลับทางการค้า ในด้านสิ่งที่คุ้มครอง ตัวอย่างงานคอมพิวเตอร์ วิธีได้สิทธิ อายุคุ้มครอง และกฎหมายไทย](/images/weeks/w13-ip-types.svg)

สิ่งที่ต้องตรวจในงาน Module 4 (Computer Vision): **dataset** ภาพมี license ของตัวเอง (เช่น CC BY ต้องให้เครดิต, CC BY-NC ห้ามใช้เชิงพาณิชย์), **pre-trained model** เช่น MobileNetV2 มีเงื่อนไขของผู้เผยแพร่, **ภาพในสไลด์** ที่ค้นจากเว็บไม่ได้แปลว่าใช้ได้ฟรี และ **ผลลัพธ์จาก generative AI** ยังมีสถานะทางลิขสิทธิ์ไม่แน่นอน เพราะกฎหมายลิขสิทธิ์โดยทั่วไปคุ้มครองงานที่มนุษย์สร้างสรรค์ จึงควรเปิดเผยการใช้ AI และตรวจสอบกับแหล่งต้นฉบับเมื่อจะนำไปใช้จริง

### 4) เลือก open source license ให้เป็น
![สเปกตรัม software license จาก permissive เช่น MIT และ Apache-2.0 ไปสู่ weak copyleft เช่น LGPL และ MPL ไปสู่ strong copyleft เช่น GPL และ AGPL จนถึง proprietary](/images/weeks/w13-license-spectrum.svg)

| License | ใช้ในซอฟต์แวร์ปิดได้ไหม | ต้องเปิด source เมื่อใด | จุดที่ต้องจำ |
|---|---|---|---|
| MIT / BSD | ได้ | ไม่ต้อง | เก็บข้อความ copyright และ license ไว้ |
| Apache-2.0 | ได้ | ไม่ต้อง | ต้องแนบ NOTICE แจ้งไฟล์ที่แก้ และมีข้อให้สิทธิ patent |
| LGPL-3.0 | ลิงก์ใช้ได้ | เมื่อแก้ตัว library แล้วแจกจ่าย | ผู้ใช้ต้องเปลี่ยน library เองได้ |
| GPL-3.0 | ไม่ได้ ถ้าแจกจ่ายงานดัดแปลง | เมื่อแจกจ่ายโปรแกรม | งานดัดแปลงต้องใช้ GPL ด้วย |
| AGPL-3.0 | ไม่ได้ | แม้แค่ให้บริการผ่านเครือข่าย | สำคัญกับ web service/SaaS |

กฎง่าย ๆ: ก่อน `pip install` หรือ copy โค้ดจาก GitHub ให้เปิดไฟล์ `LICENSE` ทุกครั้ง repo ที่ไม่มี license ไม่ได้แปลว่าเป็นสาธารณะ แต่แปลว่าเจ้าของยังสงวนสิทธิ์ทั้งหมด

### 5) PDPA ฉบับย่อสำหรับนักพัฒนา
| ประเด็น | PDPA (ไทย) | GDPR (EU) |
|---|---|---|
| ปีที่ใช้ | ประกาศ 2562 บังคับเต็มรูปแบบ 1 มิ.ย. 2565 | บังคับใช้ 25 พ.ค. 2018 |
| ฐานทางกฎหมาย | consent, สัญญา, หน้าที่ตามกฎหมาย, ประโยชน์สำคัญต่อชีวิต, ภารกิจสาธารณะ, ประโยชน์โดยชอบด้วยกฎหมาย, งานวิจัย/สถิติ | ใกล้เคียงกัน (6 ฐาน) |
| แจ้งเหตุข้อมูลรั่ว | ภายใน 72 ชั่วโมง | ภายใน 72 ชั่วโมง |
| บทลงโทษ | ปรับทางปกครองสูงสุด 5 ล้านบาท, โทษอาญา, ค่าเสียหายเชิงลงโทษไม่เกิน 2 เท่า | สูงสุด €20 ล้าน หรือ 4% ของรายได้ทั่วโลก |

ฝั่งวิศวกรแปลงกฎหมายเป็นงานออกแบบได้ทันที: ไม่ติ๊กช่อง consent ไว้ล่วงหน้า, เก็บเฉพาะ field ที่จำเป็น, เข้ารหัสข้อมูล, มีเมนูให้ผู้ใช้ขอดู แก้ไข หรือลบข้อมูล และบันทึก log การเข้าถึง (เชื่อมกับ Zero Trust ใน W12) ดูรายละเอียดเพิ่มใน [หัวข้อ 5](/module/13/05) และ [หัวข้อ 4](/module/13/04) ฝึกต่อใน [Lab 13](/lab/13)

### สรุปสั้น
- จริยธรรมถาม "ควรทำไหม" กฎหมายถาม "ทำได้ไหม" ระบบที่ดีต้องผ่านทั้งสองด่าน
- วิเคราะห์กรณีด้วย 6 ขั้น: ข้อเท็จจริง → ประเด็น → ACM Code → PDPA/IP → ทางเลือก → บันทึก
- ใบหน้า ลายนิ้วมือ และเสียงที่ใช้ระบุตัวตนเป็นข้อมูลอ่อนไหว ต้องเข้มงวดกว่าข้อมูลทั่วไป
- ลิขสิทธิ์ได้อัตโนมัติ คุ้มครองโค้ดไม่ใช่ไอเดีย ส่วนสิทธิบัตรต้องยื่นจด และโปรแกรมล้วนจดในไทยไม่ได้
- อ่าน license ก่อนใช้เสมอ: permissive ใช้ง่าย, copyleft ต้องเปิด source เมื่อแจกจ่าย
- เตรียมสอบ: ดู [แนวทางเตรียมสอบ](/exam-prep)

## กิจกรรมในชั้นเรียน / ปฏิบัติการ
อภิปรายกรณีศึกษา generative AI ใช้สร้างงานส่งรายวิชา แล้วให้ผู้เรียนเขียน policy การใช้ AI ที่ยุติธรรมและตรวจสอบได้

2. ข้อมูลส่วนบุคคลตาม PDPA คืออะไร?
3. open source license สำคัญต่อโครงงานอย่างไร?

## Research เพิ่มเติมและแหล่งอ้างอิง
**หัวข้อวิจัยเสริม:** Ethics, PDPA, UNESCO AI Ethics และ EU AI Act

- ACM Code of Ethics ใช้เป็นฐานอภิปรายว่าผู้พัฒนาระบบต้องคำนึงถึง public good, avoiding harm, privacy, honesty และ professional competence

- UNESCO AI Ethics และ EU AI Act ช่วยให้เห็นทิศทางสากลของ AI governance: human rights, transparency, fairness, human oversight และ risk-based regulation
