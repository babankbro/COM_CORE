🧠 5. โครงคำตอบกรณีศึกษา 5 ขั้น

โจทย์: smart classroom นับคนด้วยกล้อง + AI แล้วปรับแอร์ผ่าน IoT

  1. Architecture: กล้อง/ESP32 → edge model → MQTT → server + DB → dashboard → actuator
  2. Data flow: ภาพใบหน้า = ข้อมูลส่วนบุคคล → ลดเหลือ "จำนวนคน" ที่ edge
  3. Risk: นับผิดเมื่อแสงน้อย (W9) · รหัสผ่านเริ่มต้นของอุปกรณ์ (W11–12) · เก็บภาพเกินจำเป็น (W13)
  4. Mitigation: ทดสอบหลายสภาพแสง · MQTT over TLS + auth ต่ออุปกรณ์ · ไม่ส่งภาพขึ้น cloud · ป้ายแจ้ง + ระยะเวลาเก็บ
  5. Trade-off + operation: edge เป็นส่วนตัวกว่าแต่ดูแลอุปกรณ์มาก → CI/CD + monitoring (W14)

ได้คะแนนดี = หลักการ + ตัวอย่างจากโจทย์ + trade-off (ไม่ใช่ท่องนิยามอย่างเดียว)

✍️ 6. ข้อฝึกก่อนสอบ
  1. train accuracy 99% แต่ test 70% เกิดอะไรขึ้น แก้ได้อย่างไร (W9)
  2. chatbot ตอบระเบียบมหาวิทยาลัยผิด ใช้ RAG + vector database ช่วยอย่างไร (W10)
  3. เมื่อใดควรประมวลผลที่ edge แทน cloud (W11)
  4. ransomware เข้ารหัสฐานข้อมูล กระทบ CIA ข้อใด เสนอ mitigation 3 ข้อ (W12)
  5. ใช้ library GPL-3.0 ในแอปที่จะขายแบบปิด source ได้หรือไม่ (W13)
  6. ระบบสแกนใบหน้าเข้าหอพักมีประเด็น PDPA อะไร (W13)
  7. เรียง issue → PR → CI → deploy และบอกว่าแต่ละขั้นตรวจอะไร (W14)
  8. PUE ลดจาก 1.6 เป็น 1.3 หมายความว่าอย่างไร (W7, W15)
⚠️ ข้อผิดพลาดที่พบบ่อย
  • ตอบกรณีศึกษาด้วยนิยามล้วน ไม่ผูกกับโจทย์ ไม่มี trade-off
  • คิดว่า RAG = train model ใหม่ · คิดว่า hashing ถอดกลับได้
  • สับสน MQTT broker กับ publisher/subscriber
  • ลืมประเด็น PDPA/bias ในระบบที่ใช้กล้องหรือข้อมูลนักศึกษา
  • PUE ยิ่งสูงยิ่งดี (ผิด: ยิ่งใกล้ 1.0 ยิ่งดี)
