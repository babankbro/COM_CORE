🔌 1. Embedded System และ MCU

Embedded system = คอมพิวเตอร์ที่ฝังในอุปกรณ์เพื่อทำงานเฉพาะ ทรัพยากรจำกัด (RAM ระดับ KB–MB) ต้องทำงานตามเวลา (real-time) และประหยัดพลังงาน

Sensorรับรู้โลกจริง → สัญญาณไฟฟ้า (อุณหภูมิ, แสง, PIR)
Actuatorรับคำสั่ง → ลงมือทำ (รีเลย์, มอเตอร์, buzzer)
RTOSOS ที่จัดลำดับงานคาดเดาเวลาได้ (deterministic) เช่น FreeRTOS
ประเด็นMCU (ESP32, Arduino, STM32)MPU (Raspberry Pi, PC)
องค์ประกอบCPU+RAM+I/O ในชิปเดียวCPU ต่อ RAM/storage ภายนอก
ซอฟต์แวร์bare-metal / RTOSLinux เต็มรูปแบบ
พลังงาน · บูตmA, deep sleep µA · msหลายวัตต์ · หลายวินาที

ESP32 รุ่นดั้งเดิม: Xtensa dual-core 240 MHz · SRAM 520 KB · Wi-Fi 2.4 GHz + Bluetooth · ADC 12-bit (0–4095)

🏗️ 3. สถาปัตยกรรม IoT 4 ชั้น
Perception → Network → Edge/Fog → Application & Cloud
  • Network: PAN (BLE, Zigbee) · WLAN (Wi-Fi) · LPWAN (LoRaWAN, NB-IoT: ไกลหลาย กม. กินไฟต่ำ)
  • Edge/Fog: กรอง/รวมข้อมูล, TinyML ตัดสินใจเร็ว, buffer เมื่อเน็ตหลุด → ลด latency และ bandwidth
  • Cloud: broker, ฐานข้อมูล time-series, analytics, dashboard · ข้อมูลไหลขึ้น คำสั่งไหลลง

🔎 8. ไล่ข้อมูล 1 ค่า: sensor → dashboard
  1. ESP32 อ่าน BME280 ผ่าน I2C (0x76) ได้ 27.5 °C
  2. PUBLISH building5/EN301/temperature = 27.5 · QoS 1 · retain (แพ็กเก็ตเพียง 37 byte ตาม MQTT 3.1.1)
  3. Broker ตอบ PUBACK · ถ้าไม่ได้รับ client ส่งซ้ำ (flag DUP) → อาจได้ค่าซ้ำ
  4. Broker ส่งต่อให้ dashboard ที่ subscribe building5/+/temperature ด้วย QoS 0 → ขานี้ใช้ QoS 0
  5. Dashboard แสดงค่า + เก็บลงฐานข้อมูล time-series · หน้าจอที่เพิ่งเปิดเห็น 27.5 ทันทีจาก retained

ความน่าเชื่อถือต้องออกแบบทั้งเส้นทาง ไม่ใช่แค่ฝั่งส่ง

📮 5. MQTT: topic, wildcard และ QoS

Publisher ส่งไปที่ building5/EN301/temperature · broker จับคู่กับ subscription แล้วกระจายต่อ (ผู้ส่ง-ผู้รับไม่ต้องรู้ IP กัน)

+แทน 1 ระดับพอดี: building5/+/temperature = ทุกห้อง
#ระดับนี้และทุกระดับลูก ต้องอยู่ท้าย: building5/EN301/#
QoSรับประกันแพ็กเก็ตใช้กับ
0at most once (อาจหาย)PUBLISHค่า sensor ส่งถี่
1at least once (อาจซ้ำ)+PUBACKแจ้งเตือน
2exactly oncePUBREC/REL/COMPคำสั่งห้ามซ้ำ
Retainedbroker เก็บค่าล่าสุดต่อ topic ให้ subscriber ใหม่ทันที
LWT"จดหมายสั่งเสีย" ฝากตอน CONNECT broker ประกาศเมื่อหลุดผิดปกติ
Keep aliveเงียบเกิน 1.5 × keep alive → broker ถือว่าหลุด
🐍 6. MicroPython: I2C → MQTT (ESP32)
from machine import Pin, I2C from umqtt.simple import MQTTClient import time i2c = I2C(0, scl=Pin(22), sda=Pin(21), freq=100000) print(i2c.scan()) # [118] = 0x76 คือ BME280 BASE = b"building5/EN301/" c = MQTTClient("esp32-en301", "192.168.1.10", keepalive=60) c.set_last_will(BASE + b"status", b"offline", retain=True) c.connect() c.publish(BASE + b"status", b"online", retain=True) while True: t = read_temp(i2c) # ฟังก์ชันอ่าน sensor ของเรา c.publish(BASE + b"temperature", str(t).encode(), retain=True, qos=1) time.sleep(10)

ทดสอบฝั่งรับ: mosquitto_sub -h 192.168.1.10 -t "building5/+/temperature" -v

🧠 7. TinyML และ Edge AI

รันโมเดลเล็กบน MCU/edge (quantization เป็น int8, pruning) → latency ต่ำ, ทำงานได้แม้ไม่มีเน็ต, ส่งข้อมูลดิบออกน้อยลง (privacy) · ตัวอย่าง: keyword spotting, ตรวจการสั่นของมอเตอร์ (predictive maintenance)

⚠️ ข้อผิดพลาดที่พบบ่อย
  • ต่อแรงดัน 5 V เข้าขา GPIO/ADC ของ ESP32 ซึ่งรับได้ 3.3 V
  • คิดว่า building5/+ จับ building5/EN301/temperature ได้ (ไม่ได้ เพราะ + แทน 1 ระดับ)
  • ขึ้นต้น topic ด้วย / หรือสะกดตัวพิมพ์ต่างกัน (topic แยกตัวพิมพ์เล็ก-ใหญ่)
  • ตั้ง QoS 2 ฝั่งส่ง แต่ subscribe ด้วย QoS 0 → ได้จริงแค่ QoS 0 (ใช้ค่าที่ต่ำกว่า)
  • เปิด broker สาธารณะโดยไม่มี username/password, TLS และ ACL ราย topic
  • ใช้ time.sleep ยาว ๆ ใน loop ทำให้ไม่ตอบสนองคำสั่งที่ subscribe ไว้
✅ เช็กความเข้าใจ
  • อธิบายความต่างของ sensor กับ actuator และ MCU กับ MPU ได้
  • วาดสถาปัตยกรรม IoT 4 ชั้นของโครงงานตัวเองพร้อมระบุโปรโตคอลแต่ละชั้นได้
  • บอกได้ว่า filter +/+/humidity จับ topic ใดบ้าง
  • เลือก QoS ให้เหมาะกับข้อมูลแต่ละชนิดและให้เหตุผลได้
  • เขียนโค้ด publish ค่า sensor และใช้ retained + LWT แสดงสถานะ online/offline ได้
