## คำถามนำ
การนำเสนอที่ดีแสดงทั้งระบบ ผลลัพธ์ และการเรียนรู้ของทีมอย่างไร?

## ผลลัพธ์การเรียนรู้ย่อย
1. เตรียมสไลด์และ demo ที่ตอบโจทย์ rubric
2. สื่อสาร architecture, implementation, test และ limitation
3. ฝึกตอบคำถามเชิงเทคนิคและเชิงจริยธรรม

## แก่นความรู้ที่ต้องเข้าใจ
- การนำเสนอ project ไม่ใช่เล่าเฉพาะฟีเจอร์ แต่ต้องอธิบายปัญหา วิธีออกแบบ หลักฐานการทำงาน และ trade-off
- demo ที่ดีต้องมี fallback เช่น screenshot/video/log หากระบบสดมีปัญหา
- ทีมควรแบ่งบทบาทการพูดให้สะท้อนการทำงานจริงและพร้อมตอบคำถามทุกคน

## เนื้อหาเรียนรู้
- โครงเรื่องสไลด์ควรเรียง: problem → users → architecture → key implementation → demo → testing/result → limitation → next step
- ให้ผู้เรียนเตรียม architecture diagram ที่แสดง hardware/software/data/network/security ในภาพเดียว เพื่อเชื่อมกลับรายวิชา
- ฝึก Q&A ด้วยคำถาม rubric: ทำไมเลือกเทคโนโลยีนี้, ความเสี่ยงคืออะไร, ข้อมูลมาจากไหน, ถ้าขยายระบบต้องเปลี่ยนอะไร

## กิจกรรมในชั้นเรียน / ปฏิบัติการ
จัด rehearsal แบบจับเวลา 7-10 นาที พร้อม peer feedback ตาม rubric และรายการแก้ไขก่อนนำเสนอจริง

## คำถามตรวจความเข้าใจ
1. สไลด์ใดพิสูจน์ว่า project ทำงานจริง?
2. limitation ควรพูดอย่างไรให้เป็นมืออาชีพ?
3. ทีมควรตอบคำถามที่ไม่รู้คำตอบอย่างไร?

## ชิ้นงาน / หลักฐานการเรียนรู้
- สรุปแนวคิด 1 หน้า หรือ concept map ของสัปดาห์นี้
- ผลกิจกรรม/โค้ด/diagram ตามโจทย์ประจำสัปดาห์
- คำตอบสะท้อนคิด: วันนี้เข้าใจอะไรเพิ่ม และยังสงสัยอะไร

## Research เพิ่มเติมและแหล่งอ้างอิง
**หัวข้อวิจัยเสริม:** Project presentation evidence and assessment

- การนำเสนอโครงงานควรมีหลักฐาน 4 แบบ: requirement evidence, architecture evidence, implementation evidence และ evaluation evidence
- ให้ผู้เรียนอธิบาย trade-off เช่น performance vs cost, accuracy vs privacy, cloud vs edge, manual deployment vs CI/CD
- ควรประเมินทั้งผลลัพธ์และกระบวนการทีม: version history, issue tracking, test result, demo reliability และการตอบคำถาม
