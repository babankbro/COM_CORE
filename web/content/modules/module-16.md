## คำถามนำ
การนำเสนอที่ดีแสดงทั้งระบบ ผลลัพธ์ และการเรียนรู้ของทีมอย่างไร?

## ผลลัพธ์การเรียนรู้ย่อย
1. เตรียมสไลด์และ demo ที่ตอบโจทย์ rubric
2. สื่อสาร architecture, implementation, test และ limitation
3. ฝึกตอบคำถามเชิงเทคนิคและเชิงจริยธรรม

## แก่นความรู้ที่ต้องเข้าใจ
- การนำเสนอ project ไม่ใช่เล่าเฉพาะฟีเจอร์ แต่ต้องอธิบายปัญหา วิธีออกแบบ หลักฐานการทำงาน และ trade-off
- demo ที่ดีต้องมี fallback เช่น screenshot/video/log หากระบบสดมีปัญหา
- ทีมควรแบ่งบทบาทการพูดให้สะท้อนการทำงานจริงและพร้อมตอบคำถามทุกคน

## เนื้อหาเรียนรู้
- โครงเรื่องสไลด์ควรเรียง: problem → users → architecture → key implementation → demo → testing/result → limitation → next step
- ให้ผู้เรียนเตรียม architecture diagram ที่แสดง hardware/software/data/network/security ในภาพเดียว เพื่อเชื่อมกลับรายวิชา
- ฝึก Q&A ด้วยคำถาม rubric: ทำไมเลือกเทคโนโลยีนี้, ความเสี่ยงคืออะไร, ข้อมูลมาจากไหน, ถ้าขยายระบบต้องเปลี่ยนอะไร

## 🧭 อธิบายเพิ่มเติม (ฉบับขยาย)

### 1) การนำเสนอคือ "การพิสูจน์" ไม่ใช่ "การโฆษณา"
ลองนึกถึงทนายในศาล ทนายที่ดีไม่ได้พูดว่า "ลูกความผมบริสุทธิ์แน่นอน" ซ้ำ ๆ แต่เรียงหลักฐานทีละชิ้นจนผู้ฟังสรุปเองได้ การนำเสนอโครงงานก็เช่นกัน กรรมการไม่ได้ต้องการฟังว่าระบบ "ดีมาก" แต่ต้องการเห็นหลักฐาน 4 แบบ:
- **Requirement evidence:** ปัญหาจริงคืออะไร ใครคือผู้ใช้ และวัดความสำเร็จอย่างไร
- **Architecture evidence:** diagram ที่เห็นทั้ง hardware, software, data, network และ security
- **Implementation evidence:** โค้ด วงจร commit history หรือ CI ที่ผ่าน
- **Evaluation evidence:** ตารางทดสอบ accuracy latency หรือผลจากผู้ใช้จริง

### 2) Storyline 10 นาทีที่แนะนำ
![แผนภาพแบ่งเวลานำเสนอ 10 นาทีเป็น 8 ช่วง ได้แก่ problem, users และ requirement, architecture, key implementation, live demo, testing และ result, limitation และ next step พร้อมหลักฐานที่ต้องแสดงในแต่ละช่วง](/images/weeks/w16-storyline.svg)

ตัวอย่าง storyline ของโครงงาน **AI Object Detection + IoT Dashboard** (รวม 4 โมดูล):
1. **Problem (1 นาที):** "ห้องปฏิบัติการเปิดแอร์ทิ้งไว้ทั้งที่ไม่มีคน เราวัดได้ว่า 3 ใน 10 คาบห้องว่างเกิน 30 นาที" (ใช้ตัวเลขที่ทีมเก็บเอง)
2. **Users & requirement (1 นาที):** เจ้าหน้าที่อาคารต้องการเห็นจำนวนคนแบบ real-time พร้อม acceptance criteria ที่วัดได้
3. **Architecture (1.5 นาที):** กล้อง → model (Module 4) → API → database (Module 2) → MQTT ไปบอร์ด (Module 3) → dashboard พร้อมบอกว่าจุดใดเก็บข้อมูลส่วนบุคคล
4. **Key implementation (1.5 นาที):** โชว์โค้ดสำคัญเพียง 1–2 จุด เช่น ฟังก์ชัน preprocess และการ publish MQTT ไม่ไล่อ่านทั้งไฟล์
5. **Live demo (2 นาที):** demo สดตาม script ที่ซ้อมแล้ว และเตรียมวิดีโอสำรองเปิดได้ใน 1 คลิก
6. **Testing & result (1.5 นาที):** ตารางผลทดสอบ เช่น ภาพทดสอบกี่ภาพ ถูกกี่ภาพ latency เฉลี่ยเท่าไร และ CI ที่ผ่าน
7. **Limitation (45 วินาที):** "แสงน้อยทำให้นับผิด" และ "ภาพใบหน้าไม่ถูกเก็บ เราเก็บแค่จำนวนคน" (เชื่อม PDPA จาก W13)
8. **Next step (45 วินาที):** สิ่งที่จะทำต่อ และสรุปคุณค่าใน 1 ประโยค

### 3) สไลด์ที่ดีกับสไลด์ที่ควรเลี่ยง
| ประเด็น | ควรทำ | ควรเลี่ยง |
|---|---|---|
| ปริมาณข้อความ | 1 ข้อความหลักต่อสไลด์ + ภาพ/diagram | ย่อหน้ายาวที่อ่านตามสไลด์ |
| ตัวเลข | ตัวเลขจากการทดสอบจริงพร้อมเงื่อนไข | "แม่นยำสูงมาก" โดยไม่มีตัวเลข |
| Demo | script ชัด + วิดีโอสำรอง | เปิดโปรแกรมครั้งแรกบนเวที |
| Limitation | บอกตรง ๆ พร้อมแนวทางแก้ | ซ่อนไว้แล้วถูกกรรมการพบเอง |
| การแบ่งบทพูด | แต่ละคนพูดส่วนที่ตัวเองทำจริง | คนเดียวพูดทั้งหมด |
| แหล่งอ้างอิง | ระบุ dataset, model, library และการใช้ AI | ใช้ภาพ/โค้ดคนอื่นโดยไม่ให้เครดิต |

### 4) ฝึก Q&A: สูตร 5 ขั้น
![ขั้นตอนตอบคำถาม 5 ขั้น ได้แก่ ฟังให้จบ ทวนคำถาม ตอบตรง 1 ประโยค ยกหลักฐาน และบอกข้อจำกัดพร้อมทางต่อ และวิธีรับมือเมื่อไม่รู้คำตอบ](/images/weeks/w16-qa-framework.svg)

**ตัวอย่างคำถามและแนวตอบ**
- **"ทำไมเลือก MQTT แทน HTTP?"** → "MQTT เป็นแบบ publish/subscribe ที่ overhead ต่ำ เหมาะกับบอร์ดที่ส่งข้อมูลถี่ ๆ ในทีมเราวัดว่า ... (หลักฐาน) แต่ถ้าต้องการ request/response แบบเว็บทั่วไป HTTP ก็ยังเหมาะกว่า (trade-off)"
- **"model แม่นยำแค่ไหน และทดสอบกับข้อมูลอะไร?"** → ตอบเป็นตัวเลขจาก test set ที่แยกจาก training ชัดเจน และบอกขนาด test set ไม่ใช้ accuracy จาก training
- **"ระบบนี้มีประเด็น PDPA ไหม?"** → ระบุว่าข้อมูลใดเป็นข้อมูลส่วนบุคคล เก็บที่ใด นานเท่าใด ใครเข้าถึงได้ และทำ data minimization อย่างไร
- **"ถ้าใช้ทั้งอาคาร 50 ห้อง ต้องเปลี่ยนอะไร?"** → พูดถึง scalability: broker, database, การ deploy แบบ container และ monitoring (เชื่อม W7, W14)
- **"ใครทำส่วนนี้?"** → เจ้าของส่วนตอบเอง และชี้ commit/PR ของตนได้

ถ้าไม่รู้คำตอบ ให้พูดว่า "ส่วนนี้ทีมยังไม่ได้ทดสอบครับ/ค่ะ ถ้าจะตอบให้แน่นอนเราจะทดลองโดย ... แล้วส่งผลให้ภายหลัง" ซึ่งแสดงความซื่อสัตย์ทางวิชาชีพ (ACM 1.3) ดีกว่าการเดา

### 5) Checklist ก่อนขึ้นเวที (rehearsal)
- จับเวลาจริง 7–10 นาที อย่างน้อย 2 รอบ และให้เพื่อนอีกทีมให้คะแนนตาม rubric 5 เกณฑ์ (ความถูกต้องเชิงเทคนิค, การประยุกต์/สร้างสรรค์, การสื่อสาร, การทำงานเป็นทีม, การตอบคำถาม)
- ทดสอบโปรเจกเตอร์ อินเทอร์เน็ต และ broker ก่อนเวลา มี hotspot สำรอง
- เตรียมสไลด์ backup เช่น diagram ละเอียดและตารางผลเต็ม ไว้ตอบคำถาม
- repository เปิดดูได้ README บอกวิธีรัน และ CI ล่าสุดผ่าน ([Lab 14](/lab/14), [Lab 15](/lab/15))
- ทบทวนหลักการจาก [หัวข้อ 5 ของสัปดาห์ 14](/module/14/05) เรื่องการเตรียม capstone

### สรุปสั้น
- นำเสนอด้วยหลักฐาน 4 แบบ: requirement, architecture, implementation, evaluation
- storyline: problem → users → architecture → implementation → demo → result → limitation → next step
- demo ต้องมี script และวิดีโอสำรองเสมอ
- พูดถึง limitation และ trade-off อย่างตรงไปตรงมาพร้อมแนวทางแก้
- ตอบคำถามด้วยสูตร: ฟัง → ทวน → ตอบตรง → หลักฐาน → ข้อจำกัด/ทางต่อ
- หลังนำเสนอให้เตรียมสอบปลายภาคต่อ: ดู [แนวทางเตรียมสอบ](/exam-prep)
