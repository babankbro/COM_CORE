## คำถามนำ
ทำไมการคิดเชิงอัลกอริทึมยังสำคัญ แม้มี AI ช่วยเขียนโค้ด?

## ผลลัพธ์การเรียนรู้ย่อย
1. ออกแบบขั้นตอนแก้ปัญหาด้วย decomposition และ abstraction
2. เขียน pseudocode/flowchart สำหรับปัญหาง่าย
3. วิเคราะห์ Big-O เบื้องต้นและใช้ AI assistant อย่างรับผิดชอบ

## แก่นความรู้ที่ต้องเข้าใจ
- algorithm คือขั้นตอนชัดเจน มีอินพุต เอาต์พุต และจบได้ ไม่ใช่แค่โค้ดในภาษาใดภาษาหนึ่ง
- Big-O ช่วยคิดว่าเมื่อข้อมูลใหญ่ขึ้น โปรแกรมจะช้าลงอย่างไร
- AI assistant ช่วยเร่งงานเขียนโค้ดได้ แต่ผู้เรียนยังต้องตรวจตรรกะ ทดสอบ และรับผิดชอบผลลัพธ์

## เนื้อหาเรียนรู้
- ให้เริ่มจากปัญหาในชีวิตประจำวัน เช่นหาคะแนนสูงสุดในรายชื่อ แล้วแปลงเป็น decomposition, pseudocode และ flowchart
- เปรียบเทียบ linear search กับ binary search เพื่อให้เห็นว่าอัลกอริทึมต่างกันทำให้ประสิทธิภาพต่างกัน แม้คำตอบสุดท้ายเหมือนกัน
- สาธิตการใช้ AI ช่วยเขียนโค้ดอย่างถูกวิธี: เขียนโจทย์ให้ชัด ขอ test cases ขออธิบาย complexity แล้วผู้เรียนต้องรันและตรวจเอง

### 1. อัลกอริทึมเหมือน "สูตรอาหาร" ที่ใครทำตามก็ได้ผลเหมือนกัน

สูตรอาหารที่ดีบอกว่าต้องใช้วัตถุดิบอะไร (input) ได้อาหารอะไร (output) แต่ละขั้นชัดเจนจนคนอ่านไม่ต้องเดา และมีขั้นสุดท้ายที่ทำให้ "เสร็จ" สูตรที่เขียนว่า "ปรุงรสตามชอบ" จึงยังไม่ใช่อัลกอริทึมที่ดี เพราะสองคนทำตามแล้วได้ผลต่างกัน อัลกอริทึมก็เช่นเดียวกัน ต้องมีคุณสมบัติ 5 ข้อ

| คุณสมบัติ | ความหมาย | ตัวอย่างที่ผิด |
|---|---|---|
| Input | รับข้อมูลเข้า 0 ตัวขึ้นไป ระบุชนิดชัด | ไม่บอกว่ารับคะแนนเป็นตัวเลขหรือข้อความ |
| Output | ให้ผลลัพธ์อย่างน้อย 1 อย่าง | วนทำงานแต่ไม่คืนค่าหรือแสดงผล |
| Definiteness | ทุกขั้นชัดเจน ตีความได้ทางเดียว | "เลือกคนที่เก่ง ๆ" |
| Finiteness | จบในจำนวนขั้นจำกัด | `while True:` ที่ไม่มีทางออก |
| Effectiveness | แต่ละขั้นทำได้จริงด้วยเครื่องมือที่มี | "หาจำนวนเฉพาะที่มากที่สุด" (ไม่มีอยู่จริง) |

ภาษาโปรแกรมเป็นเพียง "ภาษาที่ใช้เขียนสูตร" อัลกอริทึมเดียวกันเขียนได้ทั้ง Python, C หรือ pseudocode นี่คือเหตุผลที่ต้องฝึกคิดอัลกอริทึมก่อน แล้วค่อยเลือกภาษา (หรือให้ AI แปลงเป็นภาษาที่ต้องการ)

### 2. ตัวอย่างทีละขั้น: หาคะแนนสูงสุดจากคะแนน 5 คน

![แผนภาพแสดงการคิดเชิงคำนวณ 4 ขั้น (Decomposition, Pattern, Abstraction, Algorithm) กับโจทย์หาคะแนนสูงสุด แล้วไหลต่อเป็น pseudocode โค้ด Python การทดสอบ และการวิเคราะห์ Big-O ได้ O(n) โดยถ้าทดสอบไม่ผ่านให้วนกลับไปแก้โค้ด](/images/weeks/w04-problem-to-code.svg)

**ขั้นที่ 1 คิดเชิงคำนวณ:** แยกงานเป็น รับคะแนน → เปรียบเทียบ → แสดงผล (decomposition) สังเกตว่าทุกคนถูกทำแบบเดียวกันคือ "เทียบกับค่าที่ดีที่สุดตอนนี้" (pattern) และไม่สนชื่อหรือข้อมูลอื่นนอกจากตัวเลข (abstraction)

**ขั้นที่ 2 เขียน pseudocode**

```text
best ← คะแนนตัวแรก
FOR คะแนน s ตัวที่เหลือทุกตัว
    IF s > best THEN best ← s
RETURN best
```

**ขั้นที่ 3 เขียนโค้ด Python และตามรอย (trace) ทีละรอบ** กับคะแนน `[67, 82, 74, 91, 88]`

```python
def find_max(scores):
    """คืนคะแนนสูงสุด ถ้าลิสต์ว่างให้แจ้ง ValueError"""
    if not scores:
        raise ValueError("ไม่มีคะแนนให้เปรียบเทียบ")
    best = scores[0]
    for s in scores[1:]:
        if s > best:
            best = s
    return best
```

| รอบ | s | s > best? | best หลังรอบนี้ |
|---|---|---|---|
| เริ่ม | - | - | 67 |
| 1 | 82 | ใช่ | 82 |
| 2 | 74 | ไม่ใช่ | 82 |
| 3 | 91 | ใช่ | 91 |
| 4 | 88 | ไม่ใช่ | 91 |

**ขั้นที่ 4 ทดสอบทั้งกรณีปกติและกรณีขอบ** (รันจริงแล้วผ่านทั้งหมด)

```python
assert find_max([67, 82, 74, 91, 88]) == 91
assert find_max([5]) == 5              # มีตัวเดียว
assert find_max([-3, -8, -1]) == -1    # ค่าติดลบทั้งหมด
# find_max([]) -> ValueError: ไม่มีคะแนนให้เปรียบเทียบ
```

กรณีค่าติดลบเป็นกับดักที่พบบ่อย ถ้าเริ่มต้นด้วย `best = 0` แทน `best = scores[0]` ฟังก์ชันจะตอบ 0 ซึ่งไม่ได้อยู่ในลิสต์เลย โค้ดที่ AI สร้างก็พลาดแบบนี้ได้ จึงต้องมี test ของเราเอง

**ขั้นที่ 5 วิเคราะห์ Big-O:** คะแนน n ตัว เปรียบเทียบ n − 1 ครั้ง (ข้อมูล 5 ตัวเทียบ 4 ครั้ง) จำนวนขั้นโตตาม n จึงเป็น **O(n)** และทำให้เร็วกว่านี้ไม่ได้ เพราะต้องดูคะแนนทุกตัวอย่างน้อยหนึ่งครั้งจึงมั่นใจว่าไม่มีใครสูงกว่า

### 3. Big-O เทียบกับชีวิตประจำวัน

![กราฟซ้ายแสดงเส้นการเติบโตของ O(1), O(log n), O(n), O(n log n) และ O(n²) เมื่อ n ถึง 40 กราฟขวาเป็นแท่งสเกล log แสดงจำนวนขั้นเมื่อ n เท่ากับหนึ่งล้าน ตั้งแต่ 1 ขั้นจนถึง 10 ยกกำลัง 12 ขั้น ซึ่งใช้เวลาราว 2.78 ชั่วโมงที่ความเร็ว 10 ยกกำลัง 8 ขั้นต่อวินาที](/images/weeks/w04-bigo-growth.svg)

| Big-O | เปรียบเทียบ | ตัวอย่างในโค้ด | n = 1,000,000 ใช้ราว |
|---|---|---|---|
| O(1) | เปิดล็อกเกอร์ที่รู้หมายเลขแล้ว | `d[key]`, `lst[i]` | 1 ขั้น |
| O(log n) | เปิดพจนานุกรม แบ่งครึ่งหน้าไปเรื่อย ๆ | binary search | ~20 ขั้น |
| O(n) | เดินหาเพื่อนในแถวทีละคน | linear search, หาค่าสูงสุด | 1,000,000 ขั้น |
| O(n log n) | จัดไพ่ทั้งสำรับแบบแบ่งกองแล้วรวม | `sorted()` | ~20 ล้านขั้น |
| O(n²) | ทุกคนในห้องจับมือกับทุกคน | ลูปซ้อน 2 ชั้นเทียบทุกคู่ | 10¹² ขั้น |

ตัวอย่างจับมือช่วยให้เห็นว่า O(n²) โตเร็วแค่ไหน คนหนึ่งล้านคนจับมือกันครบทุกคู่ต้องจับ n(n − 1)/2 = 499,999,500,000 ครั้ง ถ้าคอมพิวเตอร์ทำได้ 10⁸ ขั้นต่อวินาที งานขนาด 10¹² ขั้นจะใช้ราว 2.8 ชั่วโมง ส่วน O(n) ใช้เพียง 10 มิลลิวินาที การเลือกอัลกอริทึมจึงสำคัญกว่าการซื้อเครื่องที่เร็วขึ้นสองเท่า

### 4. Binary search ทีละรอบ: ทำไมต้องเรียงข้อมูลก่อน

![ตารางแสดง binary search หาเลข 77 ในลิสต์ที่เรียงแล้ว 10 ตัว แต่ละรอบช่วงค้นหาเหลือครึ่งหนึ่ง รอบ 1 mid เท่ากับ 4 ได้ 58 รอบ 2 mid เท่ากับ 7 ได้ 84 รอบ 3 mid เท่ากับ 5 ได้ 63 และรอบ 4 พบ 77 ที่ index 6 ใช้ 4 รอบ ส่วน linear search ต้องดู 7 ตัว](/images/weeks/w04-binary-search-trace.svg)

Binary search ตัดสินใจทิ้งครึ่งใดครึ่งหนึ่งได้เพราะรู้ว่า "ค่าทางซ้ายน้อยกว่าเสมอ" ถ้าลิสต์ไม่เรียง การทิ้งครึ่งซ้ายอาจทิ้งคำตอบไปด้วย จึงมีกติกาเลือกใช้ดังนี้

| สถานการณ์ | วิธีที่เหมาะ | เหตุผล |
|---|---|---|
| ค้นหา 1 ครั้งในลิสต์ที่ไม่เรียง | linear search | sort ก่อนใช้ O(n log n) ซึ่งแพงกว่า O(n) |
| ค้นหาหลายพันครั้งในลิสต์เดิม | sort ครั้งเดียวแล้ว binary search | จ่าย O(n log n) ครั้งเดียว แต่ละครั้งเหลือ O(log n) |
| ถามแค่ "มีหรือไม่มี" ซ้ำ ๆ | `set` หรือ `dict` | ค้นหาเฉลี่ย O(1) |

### 5. กระบวนทัศน์การเขียนโปรแกรม: เปรียบเหมือนวิธีจัดครัว

| กระบวนทัศน์ | เปรียบเทียบ | แนวคิดหลัก | เหมาะกับ |
|---|---|---|---|
| Procedural | ทำตามสูตรทีละบรรทัดจากบนลงล่าง | ลำดับคำสั่ง + ฟังก์ชัน | สคริปต์สั้น งานอัตโนมัติ |
| OOP | ครัวที่แต่ละสถานีมีอุปกรณ์และหน้าที่ของตัวเอง | object รวมข้อมูล (attribute) กับพฤติกรรม (method) | เกม ระบบที่มีสิ่งของหลายชนิด |
| Functional | เครื่องคั้นน้ำผลไม้ ใส่อะไรเข้าก็ได้ผลเดิมทุกครั้ง | pure function ไม่แก้ข้อมูลเดิม | แปลงข้อมูลเป็นชุด งานขนาน |

ในเกม Mini-Project 1 ตัวละครกับมอนสเตอร์เหมาะกับ OOP (class `Player` มี `hp` และ `attack()`) ส่วนการคำนวณคะแนนรวมจากลิสต์เหมาะกับแนว functional เช่น `sum(map(...))` ภาษา Python ใช้ผสมกันได้ รายละเอียดอยู่ใน [หัวข้อ 3](/module/04/03)

### 6. ทำงานกับ AI assistant แบบ "นักบินผู้ช่วย" ไม่ใช่ "นักบินอัตโนมัติ"

AI coding assistant เหมือนนักบินผู้ช่วยที่เก่งเรื่องจำและพิมพ์เร็ว แต่กัปตัน (ผู้เรียน) ยังต้องรู้เส้นทางและรับผิดชอบเมื่อเครื่องลง

| ทำแบบนี้ | แทนแบบนี้ |
|---|---|
| บอกโจทย์ อินพุต เอาต์พุต และกรณีขอบให้ชัด | "เขียนโค้ดหาค่าสูงสุดให้หน่อย" |
| ขอให้อธิบายโค้ดและ Big-O ทีละส่วน | คัดลอกไปวางโดยไม่อ่าน |
| เขียน test เองแล้วรันจริง | เชื่อว่า "รันได้ = ถูก" |
| ส่ง error message เต็ม ๆ กลับไปถาม | บอกแค่ว่า "มันพัง" |
| บันทึกว่าใช้ AI ตรงไหนใน progress log | ปิดบังการใช้ AI |

เมื่อทำงานเป็นทีม ให้ commit ทีละเรื่องเล็ก ๆ พร้อมข้อความที่บอกว่าเปลี่ยนอะไร เพื่อย้อนกลับได้ถ้าโค้ดจาก AI ทำให้ระบบพัง ดูการใช้ Git และการแก้ conflict ใน [หัวข้อ 5](/module/04/05)

### สรุปสั้น

- อัลกอริทึมต้องมี input, output, ขั้นตอนชัดเจน, จบได้ และทำได้จริง ภาษาโปรแกรมเป็นแค่เครื่องมือเขียน
- เส้นทางทำงาน: คิดเชิงคำนวณ → pseudocode/flowchart → โค้ด → test กรณีปกติและกรณีขอบ → วิเคราะห์ Big-O
- หาค่าสูงสุดเป็น O(n) เพราะต้องดูทุกตัว และควรเริ่ม `best` จากตัวแรก ไม่ใช่ 0
- เมื่อ n = 1,000,000 binary search ใช้ ~20 รอบ แต่ linear search ใช้ได้ถึง 1,000,000 รอบ และ binary search ใช้ได้กับข้อมูลที่เรียงแล้วเท่านั้น
- O(n²) ที่ n หนึ่งล้านใช้เวลาเป็นชั่วโมง การเลือกอัลกอริทึมสำคัญกว่าความเร็วเครื่อง
- AI ช่วยเขียนได้เร็ว แต่ผู้เรียนต้องอ่าน ทดสอบ วิเคราะห์ และรับผิดชอบโค้ดที่ส่ง

## 🗓️ แผนการสอนประจำสัปดาห์ (Teaching Plan)

> [!abstract] สาระสำคัญ
> **อัลกอริทึม** คือลำดับขั้นตอนแก้ปัญหาที่ชัดเจนและสิ้นสุดได้ ส่วน **โปรแกรม** คืออัลกอริทึมที่เขียนด้วยภาษาที่เครื่องเข้าใจ ทักษะแกนคือ "การคิดเชิงคำนวณ (computational thinking)"

### 🎯 วัตถุประสงค์การสอน (Learning Objectives)
1. ผู้เรียนเข้าใจแนวคิดและสามารถออกแบบอัลกอริทึมพื้นฐานเพื่อแก้ปัญหาได้ — *CLO3*
2. ผู้เรียนรู้จักกระบวนทัศน์การเขียนโปรแกรม (Programming Paradigms) แบบต่าง ๆ — *CLO3*
3. ผู้เรียนสามารถประยุกต์ใช้ AI Assistant ในการเขียนโปรแกรมได้อย่างมีประสิทธิภาพและรับผิดชอบ — *CLO3*

### 📝 สรุปเนื้อหาหัวข้อ (Topics Covered)
- แนวคิดอัลกอริทึมและโครงสร้างข้อมูลเบื้องต้น; ความซับซ้อน [Big-O Notation](/concept/big-o-notation)
- กระบวนทัศน์การเขียนโปรแกรม (Procedural, Object-Oriented, Functional)
- การทำงานร่วมกับ AI ในการเขียนโค้ด (GitHub Copilot, Cursor)
- แนวคิด [Agentic AI](/concept/agentic-ai) ในการจัดการ/เขียนโปรแกรมอัตโนมัติ

### 📖 เนื้อหาโดยละเอียด
- **การคิดเชิงคำนวณ:** decomposition, pattern recognition, abstraction, algorithm design
- **การแทนอัลกอริทึม:** ผังงาน (flowchart), รหัสเทียม (pseudocode)
- **โครงสร้างควบคุม:** ลำดับ, เงื่อนไข (if/else), วนซ้ำ (for/while)
- **ประสิทธิภาพ:** [Big-O Notation](/concept/big-o-notation) เช่น O(1), O(n), O(n²) — เปรียบเทียบอัลกอริทึมค้นหา/จัดเรียง

### 🔑 แนวคิดหลัก (Key Concepts)
[Big-O Notation](/concept/big-o-notation) · [Agentic AI](/concept/agentic-ai)

### 📈 แนวโน้มปัจจุบัน (2025–2026)
- **AI ช่วยเขียนโค้ด** โตจาก ~550 ล้าน เป็น ~4 พันล้านดอลลาร์ในปีเดียว โมเดลตีความทั้ง codebase ได้ — แต่ผู้เรียนยังต้อง **เข้าใจอัลกอริทึมเพื่อตรวจสอบ/แก้ไขโค้ดที่ AI สร้าง**
- Python ครองอันดับภาษายอดนิยมสำหรับผู้เริ่มต้นและงาน AI/data
- ประเด็นความซื่อสัตย์ทางวิชาการในการใช้ AI (เชื่อม [สัปดาห์ที่ 13: Computer Ethics & Intellectual Property](/module/13))

### 🧪 กิจกรรม/ปฏิบัติการ (OBE) — Lab 3–4
Lab 1 ชม. (วิเคราะห์ Big-O/Flowchart) + Project 1 ชม. (สรุป นำเสนอ และสาธิตการเล่นเกม) — **Module 1: Foundation & Programming**
> อ้างอิงจากแผน 4 โมดูล: ดูรายละเอียดเต็มที่ [กิจกรรมปฏิบัติการและโครงงาน](/docs/labs-projects)

### ❓ คำถามทบทวน
1. คุณสมบัติของอัลกอริทึมที่ดีมีอะไรบ้าง
2. เขียน pseudocode หาค่ามากสุดในลิสต์ พร้อมระบุ Big-O
3. ทำไมการเข้าใจอัลกอริทึมยังจำเป็นแม้มี AI ช่วยเขียนโค้ด
